# Changelog

Notable changes to slicer are recorded here. This file follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Release slices should
update the changelog; unreleased changes belong under `[Unreleased]`.

## [Unreleased]

### Changed

- `slicer ai relay-brief` on an item with no slice now fails with `no_slice` instead of `unspecified`, as every other command does; an empty required section is still `unspecified`. Branch on the code.
- `slicer template list` no longer reports a missing built-in template as `customized`: a missing file is `customized: false, missing: true` until `template set` or `reset` writes it. A project created before `relay-brief.md` existed now lists it as the default. See [commands.md](docs/commands.md).
- `relay_brief` moved from `slicer/ai.py` to `slicer/ops.py`, so `ai.py` imports no state module. The command and its JSON output are unchanged.

### Fixed

- `tests/affected.py` no longer refuses a changed non-Python file that the map does not name, such as a template added after a borrowed map was recorded. It selects the tests that read a file in that file's directory and says so on stderr. A new Python file, or a file whose directory no test reads, still refuses.
- Relay contract v6 records a failed review on the started item with `slicer note ID --text "Review FAIL: ..." --render`, adding `--kind` only when `note_kinds` configures a kind for reviews. This replaces `slicer reject`, which refuses an item that is still started at review time. The closing note and finish step still run only after `VERDICT: PASS`.
- TUI: on a narrow screen the relay board's ended line drops cells from the right, whole, as [tui.md](docs/tui.md#relay-board) describes. When the outcome and status cell does not fit, the elapsed and count cells after it are dropped too, so a bare `10m00s` no longer shows with no outcome beside it. Wide layouts are unchanged.
- `promote --file` refuses an outline source that sets `parent` or `discovered_from`, as it already refused `short_title`. Both were dropped without a word, so an author who wrote one believed it took effect. The refusal is `field_in_promote_source` (exit 2), names the key, and writes nothing. Change a parent with `set --parent`; `discovered_from` takes `add --discovered-from`, since `set` has no flag for it.
- `slicer land --branch` refuses anything except an exact short local branch name other than the checked-out branch (`invalid_branch`, nothing written). Its printed git commands use the absolute project root with `git -C`, so `--root OTHER` works from elsewhere. `land --owner NAME` records the done transition as `done --owner` does. See [landing.md](docs/landing.md).

## [1.14.0] - 2026-10-17

### Added

- `slicer relay-run end RUN --outcome pass --close-steps done|fail` first marks every step still running with that phase, under the same ledger lock and after the local events are copied into the shared ledger, so a step recorded only in a sandbox's local file is closed in the shared one. A failed write stops before the end event. The `--json` payload gains `closed_steps`, and the text names them. A plain `end` on a run with running steps prints `slicer: ended RUN with running steps: 1, 4` on stderr, still without touching them. The relay text's Close step uses `--close-steps done`, so the outer session no longer marks the orchestrator's step by hand. See [commands.md](docs/commands.md).
- `slicer import` outlines take a `short_title:` key, which sets the item's short title as `add --short-title` does and defaults to the heading. `slicer import --skeleton` now lists every key the parser accepts (`key`, `short_title`, `discovered_from` and `parent` were missing). `slicer ai instructions` and AGENTS.md name a one-item `import` (with `--dry-run` first) as the way to file an item with its fields and spec in one command. See [import.md](docs/import.md).
- `slicer retire ID --reason TEXT` retires an item exactly as `slicer remove ID --reason TEXT` does: the same status, slice move, history entry, JSON payload, `--dry-run` preview and error codes, with `command` set to `retire` in an error envelope. It takes `--force`, `--render`, `--strict` and `--json` as `remove` does, and has no `--purge`: `remove ID --purge` still deletes an item. See [commands.md](docs/commands.md).
- `slicer land ID --branch BRANCH --note TEXT` checks that the branch is merged into `HEAD` (`not_merged`) and that no relay run on the slice is still going, neither ended nor stale (`run_active`, naming the run), refusing before it writes anything. It then runs `done --render --check` and prints the git commands left for the person landing (the `.slicer` commit, `git worktree remove` for the branch's worktree, `git branch -d`). slicer still commits nothing. It takes one item; slivers keep `done`.
- `slicer ai relay-brief ID --worktree PATH --branch NAME --run RUN --step N --well-specified yes|no --split yes|no` prints a slice-specific orchestrator brief with resolved roles, parallel IDs, the project's finish policy and a commit title. `--prefer-agent` and repeatable `--select` preserve the accepted lineup; repeatable `--parallel` lists other slices. `--json` returns `{brief, roles, contract}`. The new `relay-brief.md` template supports `template set` and `reset`, with an empty built-in ENVIRONMENT block for project-owned commands. Read-only; no agents or runs are started.
- `hold_flags` (default `["needs-owner"]`) holds flagged items out of `next` and batches without changing their status. `next` and `status` report `held` candidates, and `list --held` filters waiting work. `decide ID --text|--file|--stdin` records a built-in `decision` note and clears all hold flags, even with a restrictive `note_kinds`. Set `hold_flags` to `[]` to disable holding.
- `files_section` and `overlap_ignore` config keys, and `next --batch K --disjoint`, which takes the batch greedily and skips any item whose backticked repo paths in that section overlap a chosen item's. An item whose section names no path is skipped and listed under `unknown_files`. `deps --overlap A B [C...]` prints the paths each pair shares. Both need `files_section`; it defaults to `""`, which turns them off.

### Changed

- TUI: the relay board's ended summary for a run with more than one item shows each status label with its item id (`pass · s1 review, s2 done`), so a label can be matched to its item. A single-item run keeps the bare label. See [tui.md](docs/tui.md#relay-board).
- Slice bodies load on first access. A corrupt slice body is reported with `corrupt` and its filename by commands that read it (`show ID`, `render`, `check`, `verify`), while commands that do not read it (`next`, `list`) no longer fail on it. Slice-file moves do not parse bodies and update lazy lookup paths after renaming. Explicit batch `set` reads its target bodies before any changes, refusing the batch if a target is corrupt. `show ID` avoids reading unrelated bodies; `render`, `check` and `verify` still inspect every body. File layout and rendered output are unchanged.
- `check` says when only the roadmap render is stale, as a merge leaves it (the `slicer-generated` driver keeps one side): when `ROADMAP.md` and `ROADMAP.html` are the only stale renders and nothing else fails, it adds a line that names `slicer render`, or `done --render` when landing. Its `--json` report adds `stale_render_kind`, `roadmap_only` for that case and `mixed` for any other stale render, present only when a render is stale. The exit code is unchanged. See [agents.md](docs/agents.md) and [landing.md](docs/landing.md).

### Fixed

- A shared `relay-run step --step` update absorbs the run's local events first when the step is held only in a local file, preserving its role and agent after the worktree is removed. Updates of steps already in the shared ledger do not trigger absorption.
- `edit`, `set`, `start` and `note` with a catalog record's id (for example `C01`, copied from `catalog list`) still exit 2 with `no_such_item`, and now say the id is a catalog record of its kind and name `slicer catalog show ID`, as `show` does. In a batch, the first id that is not a roadmap item decides: a catalog record gets the hint, anything else keeps the plain `no such item` message.
- Relay-run ledgers fold a step's creation after its parent's when both have the same timestamp, including nested subagents, regardless of file or line order. Absorbing child-first local events into the shared ledger no longer makes `relay-run list` report it as corrupt.
- The closing `slicer note ID --text ...` that the slice relay and its orchestrator give, the `--kind` note that `handoff_requires_note_kind` names, and the `Ready for review` note in the agent instructions, the slicer skill, AGENTS.md, CONTRIBUTING.md and the note examples in docs/agents.md and docs/commands.md now carry `--render`, so the slice's render is current when the note lands. A stale `slices/ID.md` after the note needed an extra `slicer render`. `note` still renders only when asked, `handoff` is unchanged, and the relay contract marker stays `relay v5`.
- TUI: `Q` leaves a marked item out of the relay request once it is done or retired, as if unmarked, and uses the selected item when every mark is finished. A four-digit queue number no longer leaves a digit showing beside the `[x]` mark, which is padded to the number's width. See [tui.md](docs/tui.md#relay-requests).

## [1.13.0] - 2026-10-17

### Added

- TUI: config `tui.columns` lists which of `claim`, `size` and `score` the queue row shows after the status, and in what order, so an owner can trade those cells for title room: `slicer config tui.columns '["score"]'`. The default is the layout the queue had before. An empty list shows none; an unknown or repeated name is a config error. The narrow-pane rule still drops the claim and size cells. See [configuration.md](docs/configuration.md) and [tui.md](docs/tui.md#display-and-color).
- TUI: `C` browses catalog records by kind, active then retired; Space cites or uncites the selected record on the selected queue item, with one history entry per toggle. Merge and prose-row guards refuse writes. Record management stays CLI-only. See [tui.md](docs/tui.md#catalog).

- TUI: `m` marks queue items for the session; `Q` shows an orchestrator request in queue order, using a range for adjacent slices, with per-slice relay role recommendations. With no marks it uses the selected slice. It writes nothing and launches nothing. See [tui.md](docs/tui.md#relay-requests).

- TUI: `R` shows the relay role matrix; Enter asks whether the selected slice is well-specified and split, then shows the CLI recommendation, including all five roles, selection reasons and alternatives. Esc cancels without writing. Matrix editing stays in `relay-roles`. See [tui.md](docs/tui.md#relay-roles).

- TUI: `i` cycles the detail pane between the details, the item's dependencies and its whole history, all read-only. The dependencies pane shows what the item waits on (an unsatisfied dependency marked `(blocked)`), what blocks it, what depends on it and any open slivers holding it; the history pane shows the item's whole history newest first, in the format of `slicer log --item`. In either pane `e` says it is read-only. In the dependencies pane `tab` stays in the queue; in the history pane `tab` focuses it and `j`/`k` or the arrows scroll. Selecting another item or cycling `i` resets the position. See [tui.md](docs/tui.md#dependencies-and-history).

### Changed

- TUI: the history pane reuses parsed history while the log path, modification time and size are unchanged. Appending history refreshes the pane; missing logs and read errors are retried on each redraw.

- Agent instructions and the slicer skill explain that `!` after a text `list` or `find` row number marks an unmet dependency, and point to `slicer show ID --json --lean` for `depends_on`.
- The relay board's ended summaries show the items' configured status labels beside the run outcome, keeping that cell ahead of elapsed times on narrow screens. A passed run gets `✓` only when every item has the configured done status; otherwise it gets `○`. Failed and stopped runs keep `✗` and `~`.
- The relay board colors each role on the pipeline line by its state: a finished role green, the running role cyan, a failed role red and a waiting role dim. A passed or failed ended run's outcome cell is green or red. Before, the pipeline line and an ended summary each took one color for the whole line. The TUI panel lines carry optional color spans, measured in terminal cells, that the board uses for these cells. See [tui.md](docs/tui.md#relay-board).
- The relay Setup says `relay-roles recommend` resolves each role, the orchestrator included, to its first matching row, and reports a role no row matches as unmatched (`(no matching row)` in the text, `unmatched` in the JSON), instead of saying it resolves every role to one row. The owner fills such a role at Setup; `--select` names only a row that matches the slice. The matrix and `recommend` are unchanged, and the relay contract marker stays `relay v5`.
- Contributor tooling: `tests/affected.py` records in each `.venv/affected-map.json` whether its tree had no uncommitted changes under `src/` or `tests/` when the full discover started (`"clean"`, written after `"sha"`), and `record` does the same. A worktree no longer borrows a map that is not clean, so a map recorded from uncommitted `src/` or `tests/` changes is not used once those changes are committed. A map written before the field existed is not borrowed until a full discover on a clean checkout writes one. A worktree's own map ignores the field.

### Fixed

- `relay-run end`, and a `relay-run step` that copies local events first, no longer leave the shared ledger `corrupt` when a local step's parent sat in a local file that could not be read. The step is copied without its parent, one stderr line names it and the parent it lost, and `relay-run list` reads the run.
- A `relay-run step` written to the shared ledger with a `--parent` that only a checkout's own fallback file holds first copies that run's local events into the shared ledger, as it already did when the run's begin was only local. Removing that checkout's worktree before `relay-run end` no longer leaves the shared ledger `corrupt`: `relay-run list` reads the run with both steps.

- `slicer show ID` with a catalog record's id (for example `C01`, copied from `catalog list`) still exits 2 with `no_such_item`, and now says the id is a catalog record of its kind and names `slicer catalog show ID`. An id that is neither an item nor a record keeps the plain `no such item` message.

## [1.12.0] - 2026-10-17

### Added

- `slicer add --print-id` prints only the item id and a newline, including for a keyed retry; `--render` sends its summary to stderr, and `--json` cannot be combined with the flag.

- `slicer relay-roles recommend` resolves the whole relay lineup, the orchestrator included. The matrix gains the `orchestrator` role (relay-roles schema 3, `ROLES_VERSION`): `add`, `set`, `show`, the render, `recommend` and the `slicer-relay-roles` merge driver accept its rows, and `recommend` appends it after implementer, reviewer, gate and architect. Each `roles` entry keeps `role` and `row` and adds `alternatives` (the full rows of every other row that matches the slice, in matrix order) and `selected_by` (`override`, `preferred_agent`, `matrix_order` or `unmatched`); `unmatched` lists every role whose `row` is `null`, and `--lean` keeps null rows and empty lists. New optional flags `--prefer-agent AGENT` (the first matching row on that agent, compared trimmed and ignoring case, else the first matching row) and repeatable `--select ROLE=ROW_ID` (an explicit row that matches the slice, over the preference and the order) apply to one call; without them the picks are the ones the command made before, and the launching harness has no effect. A malformed selector, an unknown role, a role selected twice, a row of another role, a row that does not match the slice and a blank agent are `bad_role_field` with the matching rows named; an unknown row is `unknown_role_row`. The text output adds the reason in brackets and the alternatives indented below each role. Still read-only: nothing is launched, probed or written. A schema 1 or 2 matrix loads without a write (its orchestrator is `unmatched`), the next mutation stamps schema 3, and an older slicer refuses a schema 3 file with `schema_too_new`, so a branch that bumps it needs the shim in [landing.md](docs/landing.md#schema-bumps).

- The slice relay is contract `relay v5` (`Contract: relay v5` in `ai relay` and `ai relay-orchestrator`). Setup, in a project with a matrix, resolves the lineup with `relay-roles recommend`, shows it once and lets the owner accept it as a whole or override individual rows; acceptance does not by itself authorize starting paid sessions, committing or landing, or answer Setup's other questions. Setup and Every brief state the routing: a native subagent on the orchestrator's harness, a headless session in the slice worktree with the same brief on another. Companion launch tooling in the agents repo must, in both directions between Codex and Claude Code, preserve shared briefs and reports, explicit model and reasoning, worktree and sandbox limits, completion and cancellation, and run tracking; this release only selects rows and has not verified launching in either direction (see [agents.md](docs/agents.md)).

- `relay-run list [RUN]` accepts an optional run id, keeping only that run in the existing text and `{runs}` JSON format. An unknown id exits 2 with `unknown_run` and the ledger paths searched. With `--active`, a known ended or stale run gives an empty list and exit 0.

- `slicer ai relay-orchestrator` prints the orchestrator's own contract for one slice and its run report. Its text carries the orchestrator's rules and report shape. It opens with the same `Contract: relay v5` line as `ai relay` (one `RELAY_CONTRACT` in `ai.py`, shared with the agents repo's `relay-orchestrator` role so a mismatch shows), follows the project's `implement_finish` and `handoff_requires_note_kind`, and `--json` returns `{"contract": "relay v5", "orchestrator": TEXT}`. Its waiting rule assumes an orchestrator's spawns can only run in the background: end the turn while a role runs, a nudge to report is not a reason to report, resume a role that stopped with its own work running, and send the final report once. Read-only.
- `add`, `set` and `import` warn on stderr when they file an item under a pass that no `prose add-pass` declared, naming the key and the command that declares it, so a pass the queue cannot order is noticed when it is made. `check` warns (exit 0) for each undeclared pass key that holds an item not done or retired, with the count. Nothing is refused, and queue order and JSON payloads do not change.
- `check` warns (exit 0, `ok` unchanged) when `.slicer/.gitignore` lacks a line `init` writes (`feedback.md`, `feedback-reported.json`, `relay-runs.jsonl`, `lock`), naming the missing lines and `slicer setup-git --attributes` on main as the fix. `setup-git --attributes` now also adds those lines, in `init`'s order after the lines the file already holds, and names them on stderr (`added LINES to PATH`); the `--json` payload is unchanged, and a complete file is not rewritten.

### Changed

- Security: the git allowlist now permits only `merge-base COMMIT COMMIT` with full commit names and no options; the unused `--is-ancestor` form is refused.
- `slicer ai relay-orchestrator` is self-contained: Order carries only the orchestrator's steps, and Gate, Every brief and Stop share their text with `ai relay`. The orchestrator no longer needs to run `ai relay` and filter its sections. The rules, `ai relay` output and contract marker are unchanged by this change.
- Fewer git processes per command. `vcs.is_repo` and the worktree lookup behind `check`, `start`, `add --id` and the render-driver hint are answered once and remembered (a repository answer only, keyed by the resolved root and by `GIT_CEILING_DIRECTORIES`, `GIT_DIR`, `GIT_WORK_TREE` and `GIT_COMMON_DIR`; "not a repository" is asked again, so a later `git init` is seen). `MERGE_HEAD` and `HEAD` are still read every time, and both `require_no_merge` checks in `main` stay. A `note` in a repo now probes `rev-parse --is-inside-work-tree` once instead of three times, and `check` with a sibling worktree starts 6 git processes instead of 8. The TUI forgets the answers each time it reloads. `verify --landed` no longer starts one `merge-base --is-ancestor` per branch, remote branch and tag: two `log` listings (`vcs.tips_outside`) name the tips outside the checked ref's history, so it starts none however many refs there are. It still reads one `show` per tip outside that history, because the closed git allowlist has no form that reads several blobs at once; that is bounded by the 1000 tips it considers. No entry in `vcs.ALLOWED` changed, and `tests/test_git_calls.py` pins the counts.
- In a git repo `relay-run` keeps one ledger per repo, `<git common dir>/slicer/relay-runs.jsonl`, shared by every worktree, with a lock file `relay-runs.lock` beside it, so removing a slice worktree no longer deletes its runs and `step` and `end` work from any worktree. `unknown_run` names the ledger path. `list` and the TUI board read the shared ledger and, as before, the `.slicer/relay-runs.jsonl` of this checkout and of each sibling worktree, so runs an older slicer recorded there still show (once, if a run is in two files); a damaged legacy file is skipped and a damaged shared ledger is `corrupt`. Outside git, and for a project below the worktree root, the ledger stays `.slicer/relay-runs.jsonl`. Existing files are only read, never moved. A `step` or `end` on a run that exists only in an old per-worktree file is refused as `unknown_run`: begin a new run.
- `slicer ai relay` now describes the nested relay: an outer session, the one the owner talks to, spawns one orchestrator per slice, and the orchestrator runs the implementer, reviewer, architect and gate. `## Roles` names the two, `## Setup` adds the orchestrator's agent, model and reasoning effort (agent type `relay-orchestrator` where the harness has one, otherwise a general-purpose agent briefed with `slicer ai relay-orchestrator`) and the environment lines every brief carries, and `## Order` gives the outer session's steps and starts the orchestrator's brief with "First run `slicer ai relay-orchestrator` and follow it.". The sentence telling one session to compact between slices is replaced by a fresh orchestrator per slice. The text opens with `Contract: relay v5`, and `ai relay --json` returns `{"contract": "relay v5", "relay": TEXT}`.
- The slice relay's `## Every brief` section asks each agent to start with the model and reasoning effort its role row names, set explicitly, and to carry the label `ID role` (also its `relay-run step --task`), so a harness's agent list shows which slice and role each agent serves and which model it runs.
- `ops.edit_section` refuses an item with no slice with the code `no_slice`, as `ops.edit_boundary` and `ops.edit_lead` already do, instead of `state`. The message is unchanged. The CLI already reported `no_slice`; a direct caller of `ops`, such as the TUI, now sees the same code.
- `slicer migrate` catches only `SlicerError` when it maps a status label, so a bug in that lookup now raises instead of being reported as a problem with the tree. A label that names no configured status is still reported as before.
- `relay-roles init` writes an example matrix whose `recommend` resolves the orchestrator on a fresh project: a Claude Code orchestrator (`r10`) first, a Codex orchestrator (`r11`) second, and a Codex implementer alternative (`r9`) after the Claude implementer rows. Default picks stay on Claude Code. The architect row (`r7`) still matches size L only, so a smaller slice leaves the architect unmatched. The example's rules are unchanged, and `init --force` numbers the new rows after every id the old matrix issued.
- Contributor tooling: a worktree with no `.venv/affected-map.json` of its own, and no `--map` given, makes `tests/affected.py` borrow a sibling worktree's map recorded at HEAD or, failing that, at the nearest ancestor of HEAD, and names that map and its commit on stderr. The working tree is diffed against that commit, so a commit made after the map was recorded selects the tests that ran a line it changed. A changed `src/slicer/` file that the map does not know, or a changed `tests/` file that is not a test module, still asks for the full suite. A borrowed map's worktree must have no uncommitted changes under `src/` or `tests/`, and its recorded commit must be a full 40-character SHA. A map recorded at a commit that is neither HEAD nor an ancestor of it is still refused, a worktree's own map is used only at HEAD, and the tool only reads the other worktree's map, never writes to it.

### Fixed

- `slicer prose add-pass KEY` reports how many existing items use KEY; an empty pass keeps its existing confirmation text.
- `add --id` refuses an id that differs only in case from one newly filed in a sibling git worktree, with `case_collision` and no write. `check` warns about the pair even when their titles match, naming both ids and the worktree because the slice files become one file on a case-insensitive filesystem. Inherited ids keep their existing behavior.
- A step a sandboxed role records through the fallback gets an id with its checkout's prefix (`c`, eight hex digits and `-`, as in `c3f9a1b2e-1`) in place of a plain number, so it cannot share an id with a step the shared ledger issues, and two checkouts are very unlikely to share one with each other. Two writers in the window the fallback opened, one through the checkout's own file and one through the shared ledger, could give two steps of a run the same id, and the later event then updated the earlier step; `docs/commands.md` (Sandboxes) recorded that as a known limit, now removed. Shared-ledger ids stay plain numbers. A step an older slicer recorded through the fallback keeps its plain number, and such a ledger still folds. `relay-run step --step` and `--parent` take the prefixed ids; a step id that is neither a number nor a checkout prefix and a number is still a `corrupt` ledger line.
- A relay role whose sandbox may write only inside its slice worktree can record `relay-run begin`, `step` and `end` again. Since the ledger moved to the git common dir (the main checkout's `.git/` for a linked worktree), a workspace-write sandbox such as Codex's default refused every write and the run showed only the steps the outer session recorded. A write the shared ledger or its lock refuses with a permission error now goes to the checkout's own `.slicer/relay-runs.jsonl` under the project lock, with one stderr line naming both paths, and never edits `.slicer/.gitignore` or `info/exclude`. `relay-run list`, the TUI board and the `step`/`end` run lookup fold the shared ledger and the local files of this checkout and its siblings into one run, ordered by time, dropping an event seen twice (`relayrun.fold` takes the events of several files). `relay-run end`, when it can write the shared ledger, first copies the run's events from the local files into it and its text names the count, so `git worktree remove` loses no step. `docs/commands.md` (Relay run ledger, Sandboxes) also describes making `<main>/.git/slicer` a writable root (Codex `sandbox_workspace_write.writable_roots`), which avoids the fallback. A step or `end` on a run that exists only in an old per-worktree file is no longer refused as `unknown_run`. A `step` written to the shared ledger for a run whose begin is only in a local file copies that run's local events first, so removing the worktree cannot leave the shared ledger `corrupt`; an event that would not fold is not copied, and a damaged local file is skipped, with one stderr line saying so.
- A write in a linked git worktree no longer edits the tracked `.slicer/.gitignore`. A project made before `init` listed every ignore line (the lock, the feedback log and sidecar, the relay ledger) used to get the missing line on its first write there, which put an unrelated change in the slice's commit. In a linked worktree whose root is the project root, the line now goes into the repo's `info/exclude` as `**/.slicer/NAME`, and the tracked file is left alone. The main checkout, a project below the worktree root and a project outside git behave as before; `init` still writes the tracked file in full. An unwritable `info/exclude` never blocks the write, as with `.slicer/.gitignore`. Lines added to `info/exclude` stay there. `vcs.linked_worktree_common_dir` answers whether a root is a linked worktree.
- `add --id` refuses an id that a sibling git worktree has already filed as an item of its own, instead of writing it and leaving `check` to warn about the merge collision. The refusal exits 2 with the new code `id_taken_elsewhere`, names the worktree and its title, and writes nothing.
- `relay-run step RUN --step N` refuses a `--task` that differs from the task the step was recorded with, though a step recorded without one may take its first. It exits 2 with `bad_run_field`, says to record a new step without `--step`, and appends nothing, so a heartbeat or a later round no longer overwrites what a step was. A heartbeat passes no `--task`, and the same task again is allowed. The relay text's `## Order` says so. A ledger that already holds an overwrite still folds as before.
- Documentation: `ARCHITECTURE.md`, `docs/getting-started.md` and the CI comment said `check` never shells out to git, and the allowlist sentence in `ARCHITECTURE.md` named `mv` and `ls-files`, which `vcs.ALLOWED` does not hold. ### Changed

The command reads no project, takes no lock, and writes nothing. `--json` is `{"workflow": "..."}`. An unreadable file is exit 3 with code `io` naming the path. A change to the recommended workflow updates that file in the same change.
- `slicer config [KEY]` prints the effective config, read-only. With no key it prints one line per top-level key, and `--json` gives the whole config. With a key, including a dotted one such as `id.prefix`, it prints the bare value, and `--json` gives `{key, value}`. An unknown key is `usage` and names the top-level keys. It reads config only, like `sections`, so it needs no index and writes nothing. An agent can now read `implement_finish` without opening `.slicer/config.json`.
- `add`, `import` and `next-id` take their id above the highest `next_id` any sibling git worktree has reached, so two worktrees stop filing different items under one id. `--dry-run` reports the same ids as the real import, and an explicit `--id` is unchanged. `slicer check` also warns (exit 0, so CI stays green) when a sibling worktree holds an id under a different title: `ID is 'A' here but 'B' in worktree NAME; the two will collide on merge. File this checkout's item under a new id before merging.` Both read only this machine's worktrees, like `list`. `store.sibling_ids` returns each readable sibling's index, and `ids.floor_from` computes the floor.
- `done` and `handoff` take `--check` with `--render`. After the change lands they run the same check as `slicer check`, stay quiet when it passes, and exit 1 with the findings on stderr when it does not. Stdout is still the item. `--check` without `--render` is a usage error and writes nothing.
- The TUI has `h` to hand off the selected item, `x` to reject it, and `l` to release its claim. They call the same operations as `slicer handoff`, `reject`, and `release`, and refuse the same cases (an item with no slice, or a project with no review status). `h` asks for an optional note and `x` for a required verdict; an empty verdict or Esc writes nothing. `h handoff` joins the shortcut strip, which stays two rows at 80 columns and one at 160 with `v view`. `x` and `l` are listed in help (`?`).
- `slicer ai instructions --rest` (and `slicer ai --rest`) prints only the parts of the guide the skill does not already carry, about 4 KB instead of 7.8 KB. It does not read the project. The skill's last line now points at it instead of the full guide. Without `--rest`, the output is unchanged.
- Bare `slicer ai` and `slicer ai --json` print the same text and JSON as `slicer ai instructions`. An unknown subcommand is still a usage error. `slicer ai skill` is unchanged.
- Text from `next`, `next --ready`, `next --show`, and `next --batch` names `slicer show ID` when the item has a slice, instead of printing the slice path. `--path` prints that path line as well and does not change JSON. A row with no slice does not gain a show hint. The promote hint stays on `next --ready` and `next --show`.
- `slicer sections` lists the configured section names and marks the ones `next` requires. `required_sections` chooses those headings. A missing key still means Implement and Check. An empty list means an empty section does not hold a slice out of `next`.
- `slicer list --in-work` and `slicer list --review` show those queues in one step. `--in-work` is started plus reviewing when that role is set. `--review` is only the review status. The TUI `v` key cycles the same views around the unfinished set.
- `implement_finish` chooses how the agent loop finishes: `done` (the default, including when the key is missing) or `handoff`. `handoff` is a config error when `review_status` is empty. `slicer ai instructions` and `slicer ai skill` use that choice when the project can be read, and otherwise print the generic text with a stderr warning. Both start with the rule to use slicer commands instead of opening tracking files.

## [1.2.0] - 2026-10-02

### Changed

- Migrate errors name the expected token and `docs/migrate-format.md`. A round-trip that differs only by trailing blank lines says so. An index with no item rows reports that no index table was found and quotes the expected header, before each "slice file has no index row" line.
- `import` and `remove` take `--render --strict`. A failed render writes nothing, including a purge that would have deleted the slice file. `--strict` without `--render`, including with `--dry-run`, is a usage error. `done` stays render-first without the flag.
- Roadmap markdown and HTML show version-shaped pass groups newest first (`v1.10` above `v1.2`, a bare `v1` below `v1.1`), then other passes in declaration order. Items with no pass follow: those that are not done, then done items. The stored queue and `next` are unchanged.
- A status change moves a slice file in the worktree only. `git mv` is no longer used, so `done`, `retire`, and `set --status` leave the index untouched. Add the old path and the new path together to record the rename.
- Documented that plain `next` offers only open and started work, so a custom status (not `exclude_flags`) holds an item out of the queue, and that `verify`'s two git checks are warnings: an unconfigured render merge driver when sibling worktrees exist, and a done item with no commit subject in the last 2000 non-merge commits. `check` still owns render freshness.
- Agent guidance requires the slicer CLI for reading and changing goals, items, slices, notes, history, and roadmap prose, including during review and planning. A missing command is reported as a roadmap item. `slicer ai skill` now covers roadmap review and planning, and distinguishes handing work off for review from marking it done.

### Added

- Version-tag publication now creates a GitHub Release from the dated changelog after PyPI publication succeeds.
- Contributor tooling: `python3 tests/affected.py --run` selects tests that executed changed lines using a locally recorded map; a missing or stale map requires the full suite.
- Top-level `--about` prints the version, description, source URL, and issues URL without a project, with `--json` support. Help shows the project description and both URLs.
- `init --id ID` sets the id the first `add` allocates, so a project can continue an earlier sequence (`slicer init --id S21`). The id must match the configured prefix and width. On an index that already has items it is refused; use `add --id` instead. `--force` over an empty index still sets the counter.
- `next --batch K` returns up to K items from the same pool as `next`, optionally narrowed with one `--tree` and an exact `--size`. A dependent follows its dependency when that dependency is in the batch. `--start` claims the whole batch under one lock and passes `--owner` through; a failure leaves every id unclaimed. An empty batch exits 2 with `{"items": [], "blocked": [...]}` and no error object. `--batch` with `--show`, `-n`, or `--status` is a usage error, as is K < 1.
- `set --add-flag` and `set --remove-flag` edit one flag without replacing the rest of the list. They cannot be combined with `--flag` or `--no-flags`.
- Items record `attempts`. `start` from open and every `reject` increment it, and `set --attempts` sets it. The index schema is now 3. A version-2 index with no `attempts` key still loads, as 0.
- `slicer reject ID --note VERDICT [--to STATUS]` sends a review or reviewing item back to the open status (or another non-lifecycle status), clears its claim, adds the verdict to the item's notes, and logs one `reject` entry carrying it. Every id is checked before anything is written. It takes `--owner`, `--json`, `--render` and `--strict`.
- `next --status review` is the reviewer's one-call pickup: the highest-priority review item, ranked and dependency-gated like `next`, with the same `--ready`/`--section`/`--lean` payloads. `--start` claims it and moves it to `reviewing`, and a later call resumes it first. Only the configured review status is accepted.
- A `reviewing` status (`reviewing_status` in config, back-filled like `review`). `start` on a review item now moves it to `reviewing` and claims it, instead of back to `started`, so an implementer's `next` no longer resumes a review in progress. `list` ranks reviewing items with started ones, sibling worktrees count them as in work, and `handoff` refuses them. Set `reviewing_status` to `""` to keep the old behaviour.
- The STATUS column in `list`, `find` and `deps` widens to fit its longest label (`reviewing`, or a project's own status), so a long label no longer shifts the rest of its row. Tables whose labels fit in 7 characters are unchanged.
- `--owner NAME` on `start`, `next --start`, `handoff`, `release` and `done`, and a `SLICER_CLAIM_OWNER` environment variable, name who claims or acts per call, ahead of `claim_owner` and the git user. Those history entries record it as `by`, and `log --by NAME` filters on it. Other history lines are unchanged.
- `slicer id-prefix [NEW]` prints the id prefix, or changes its case for new ids (for example `S` to `s`) in the index and config together. Existing ids keep their case and no slice file is renamed. A prefix that differs by more than case is refused. It takes `--dry-run`, `--json`, `--render` and `--strict`.

### Fixed

- `set --title` keeps a short title that was never chosen separately in step with the new title. A distinct short title is left unchanged.
- `promote --file` and `import` lift a boundary paragraph out of an item's lead into the scope boundary. The same paragraph in both the lead and a section is refused, and nothing is written.
- `check` and dependency edits no longer treat an edge from a retired or done item onto a retired item as drift. An open, started, or parked item that depends on a retired item still fails.
- An explicit id whose prefix differs from the configured one only in case (`add --id s05` under `S`) now advances `next_id`, and the high-water check counts it. Allocation refuses a generated id that differs from an existing id only in case (`case_collision`) instead of writing a second slice over the first on a case-insensitive filesystem.

## [1.0.0] - 2026-09-29

### Added

- `slicer handoff ID [ID ...]` hands started work to review: the status becomes the new `review_status` (default `review`, back-filled into existing configs unless another status already renders as `review`) and the claim is cleared, in one save with one `handoff` history entry per item. `next` does not offer review items and their dependents stay blocked until `done`; a reviewer finds them with `list --status review` and claims one with `start`. It refuses, writing nothing, an item that is not started or in review, or has no slice. `--render`, `--strict`, `--note` and batch ids work as on `start`. `review_status: ""` disables it.
- `slicer add` prints a non-blocking stderr hint when an open or started item is filed at importance 2, urgency 2 and no effort, and `slicer import` (dry run and real) names such items in `warnings`, so an unscored item is caught when it is filed rather than when the queue will not sort. Stdout, the JSON payload and the exit code are unchanged; a deliberate 2/2 with an effort estimate is quiet.
- `slicer start` records a claim on the item (owner and time). `slicer list` names the owner and marks other in-progress rows with `*`; `--json` includes `claim`. `slicer release` clears a claim without changing status, and `done` clears it too. The owner is config `claim_owner`, otherwise the git user name, otherwise the worktree name.
- `slicer start` warns on stderr when another branch or worktree name refers to that slice id. The current checkout is ignored, the exit code is unchanged, and `next` stays silent.
- Text `slicer list` now labels its columns and reports how many matching done or retired items the default filter hides, with a `--all` hint. JSON output remains an array.
- `slicer check` also parses the backtick `slicer ...` examples written inside a live slice's sections and fails on a flag the real parser does not know, naming the slice id, section, and flag — so a removed or renamed flag (like `--require-render`) is caught before an agent copies it into a real command. Done and retired slices are not scanned, so history keeps its old flag names; a flag merely mentioned in prose is left alone.
- `slicer init`, when run inside a git repo, prints the two `git config` lines that turn on the `slicer-generated` render merge driver, so the one-time per-clone setup is surfaced rather than buried in the docs. slicer still never runs `git config` itself. `--json` output is unchanged.
- slicer warns on stderr when its own code and the project it discovers are different worktrees of one repo — an editable install run from a sibling checkout, whose `src/` edits are not what runs. The note names both paths and suggests `PYTHONPATH=src python3 -m slicer`. It never touches stdout or the exit code, stays silent for ordinary use (code under the project, or an unrelated install), and is silenced by `SLICER_NO_CODE_WARNING`.
- `slicer setup-git` prints the two `git config` lines that turn on the `slicer-generated` render merge driver, so a clone (which never runs `init`) can enable it in one step — run the command, or `slicer setup-git | sh`. It needs no project, `--json` returns the commands as a list, and slicer still never runs `git config` itself.
- `slicer verify` warns (never fails) when the `slicer-generated` render merge driver is not configured in the current clone, pointing at `slicer setup-git`, so a forgotten setup is caught before a merge writes conflict markers. It fires only when the checkout has other worktrees (the parallel workflow the driver serves), so a single-worktree clone stays quiet; the new `render_driver_check` config flag (default true) turns it off entirely. The probe is a read-only `git config --get`; `slicer check` stays git-free and does not run it.
- `slicer list` marks an item that is started or claimed in a sibling git worktree with `wt:<name>` in the CLAIM column (a local claim or start still takes precedence), and `--json` gains a per-row `in_work_elsewhere` list. It reads each sibling worktree's real state (not branch names), so a merged or off-convention branch never produces a false mark; the lookup enumerates worktrees once and is limited to checkouts on this machine.
- `--strict`, with `--render`, keeps a mutation only when rendering succeeds. The change is rendered before it lands, and a render failure rolls the whole change back — leaving state and generated output untouched — and exits 2 with `code="render"`. `--render` alone still saves first. `done --render` already requires a successful render and now shares the same render-first path.
- `slicer next --ready` returns a bounded pickup of the next eligible item: its id, title, status, dependencies, effective score, and slice path; the slice when it has one; and the blocked list. An empty queue matches `next` (exit 2, `item: null`). `--ready` with `--show` is a usage error.
- `slicer next --ready --section NAME` repeats to return the scope boundary and those section bodies only. Omitting `--section` still returns the full slice. `--section` without `--ready` is a usage error. `--json --lean` applies to that payload.
- `slicer list --flag` filters by a free-form flag. Repeat it to match any of the named flags. The TUI filter panel offers the same flag axis, including items with no flags.

- JSON output for commands, including structured error envelopes for failures.
- A no-clone install path using an isolated Python environment.
- Roadmap commands for goals, status, dependencies, search, sorting, notes, and
  progress statistics.
- TUI search, filters, jump and help; item and slice note editing; queue
