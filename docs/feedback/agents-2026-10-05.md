## New requests

Priority means priority for an unattended agent loop: P1 = we work around
it with risk, P2 = we work around it with code, P3 = nice to have.

### U1. Say when a render is stale because slicer changed, not the state (P1)

- **Problem.** After upgrading to 1.2.0, `slicer check` fails on a clean
  tree. Done items now render in a separate trailing table, so the committed
  `ROADMAP.md`/`ROADMAP.html` are "stale" with no state change. CI and our
  test suite (`tests/run.sh:1041` runs `slicer check`) go red. An agent told
  that "a non-zero check means the work is not finished" then re-renders and
  commits a diff unrelated to its slice, or stops.
- **Evidence.** SA1. `slicer check --diff` shows only done rows moving
  between tables.
- **Proposal.**
  - Stamp the generating version in the render header comment, for example
    `<!-- GENERATED by slicer 1.2.0 ... -->`.
  - When a stale render's stamp differs from the running version, `check`
    reports the cause: `stale_render: [{"file": "ROADMAP.md", "cause":
    "renderer_version", "rendered_by": "1.1.0", "running": "1.2.0"}]`, with
    the text "rendered by slicer 1.1.0; this is 1.2.0 — run slicer render".
  - Optional: a `min_version` config key that makes an older slicer refuse
    with a dedicated code. `schema_too_new` already does this for the index.
- **Workaround.** We pin a minimum version in our doctor (our S29) and
  re-render in a separate commit.

### U2. Let a configured status satisfy dependencies (P2)

- **Problem.** Our orchestrator commits each passing slice on a run branch.
  The owner merges the run branch to `main` later. slicer's docs say to run
  `done` only after review and merge, but dependents stay blocked until
  `done`. So we either stall the queue until the owner merges, or call the
  item "done" on the run branch before it reaches `main`.
- **Evidence.** SA findings "Risks: done on a run branch". Our NOTES
  decision 2026-10-01: "PASS: commit on the run branch, then `slicer
  done`".
- **Proposal.** Add config `satisfies_dependencies: ["done", "landed"]`,
  default `["done"]`. `next`, `deps` and `check` treat those statuses as
  satisfying a dependency. `done` keeps its meaning, and `landed` is an
  ordinary custom status set with `slicer set ID --status landed`.
  `list --in-work` and `verify`'s git check do not change.
- **Workaround.** Run `done` on the run branch and document that `main` lags
  until the merge.

### U3. Typed notes, and requiring one before handoff (P1)

- **Problem.** Notes are untyped text. A reviewer kickoff that should load
  "the owner's decisions and the slice-done report" must load every note:
  review verdicts, metrics, history. Nothing makes an implementer leave a
  report before handoff. One of our implementers handed off with no report.
  Reviewers then failed slices on deviations the owner had accepted, because
  the decision was buried or never loaded.
- **Evidence.** SA4, SA5. The S26 note "Slice-done report: NOT FILED by the
  implementer". Review F17.
- **Proposal.**
  - `slicer note ID --kind KIND --text ...`, where KIND is free-form but
    validated against an optional config list, for example `["decision",
    "report", "verdict", "metrics"]`. Notes keep `kind` in JSON and it
    renders as a label.
  - `show ID --notes-kind decision --notes-kind report` (and the same on
    `next --ready`) returns only those notes.
  - Config `handoff_requires_note_kind: "report"` makes `handoff` refuse with
    code `state` ("S26 has no report note") and write nothing.
- **Workaround.** Our orchestrator greps note text for a fixed prefix and
  refuses to continue. This is brittle and unenforced for interactive
  sessions.

### U4. Provenance and idempotent filing for agent-discovered work (P2)

- **Problem.** Agents find defects mid-slice. We want them filed as
  `draft`, traceable to the slice that found them, and never duplicated when
  a session is retried or two sessions find the same thing. Today `add` has
  no provenance field, and nothing makes a repeated `add` a no-op.
  Duplicate detection means fuzzy `find` plus judgment.
- **Evidence.** SA8.
- **Proposal.**
  - `add --discovered-from ID` (and outline key `discovered_from:`): a
    validated item reference rendered on the row, and queryable with
    `list --discovered-from ID`.
  - `add --key TEXT` (and outline key `key:`): an idempotency key unique per
    project. A second `add` or import with the same key returns the existing
    item with `"existing": true` and exit 0, and writes nothing.
  - `find --title-exact TITLE` for a deterministic dedupe check.
- **Workaround.** Our orchestrator owns all filing. It runs a title-equality
  check via `find --in title --json` plus a script, and puts provenance in
  `findings:` text.

### U5. `next --status` for any custom status (P2)

- **Problem.** `next --status` accepts only the review status. Confirmed:
  `slicer next --status draft` exits 2, `usage`, "only 'review' ... is
  supported". Our approval and triage lanes use custom statuses (`draft`,
  `needs-input`). An architect or triage agent has to `list --status draft
  --json` and pick and claim items itself, losing `next`'s ranking,
  dependency gating and atomic `--start`.
- **Proposal.** Allow `next --status KEY` for any configured non-lifecycle
  status, using the same ranking and dependency gate. `--start` claims the
  item without changing status, or moves it to a status named by
  `--start-to KEY`.
- **Workaround.** `list --status draft --sort score --json` plus our own
  claim logic.

### U6. Attempt caps in `next` (P3)

- **Problem.** We allow one repair (two attempts) before an item goes to
  `blocked`. `attempts` exists, but nothing in `next` respects a cap, so the
  orchestrator must re-check after every pickup.
- **Proposal.** `next --max-attempts N` skips items with `attempts >= N` and
  lists them in a `capped` array, in the same shape as `blocked`.
  Alternatively, config `max_attempts` with `reject` moving an item to a
  configured status once the cap is reached.
- **Workaround.** Count `reject` entries in `slicer log --item ID --json`
  after each failure.

### U7. `log --since` (P2)

- **Problem.** A run report or close-out needs exactly the history of one
  run. `log` has `--limit`, `--item`, `--action` and `--by`, but no time or
  position window. We filter the full log ourselves.
- **Evidence.** SA10.
- **Proposal.** `log --since ISO8601` and `--until`. Optionally, a position
  cursor on each entry and `--since-position`, so a window stays exact
  across clock skew. Entries today carry `when, item, action, from, to,
  note` (and `by`), with no position.
- **Workaround.** `slicer log --limit 100000 --json` filtered by `when`.

### U8. Merging per-item changes made on two branches (P3, needs your check)

- **Problem.** During a run, the run branch changes item statuses and files
  drafts, while the owner approves drafts on `main`. Your docs say a genuine
  overlap in `index.json` is "yours to resolve" by hand. For an unattended
  loop, a hand merge of tracking JSON is exactly what agents are told never
  to do.
- **Caveat.** Revised 2026-10-05. We did not read `index.json`'s layout
  (your rule). We still do not know whether non-overlapping item edits
  already merge cleanly as text. If they do, what remains of this request
  reduces to documenting that. Since filing, s191 (open) adds a merge
  driver that keeps the larger `next_id` when that is the only
  disagreement, and leaves every other conflict marked. s185 (open) raises
  the allocation floor from sibling worktrees. Neither merges two
  non-overlapping item edits.
- **Proposal.** Leave `next_id` to s191. Extend that same driver so a
  three-way merge of `index.json` keeps both sides when they change
  different items, or different fields of one item, and leaves conflict
  markers only when both sides change the same field of the same item.
  s185's id-collision warning stays the error case for two items allocated
  the same id. Do not add a store outside the worktree to avoid the merge.
- **Workaround.** No queue edits on `main` during a run.
- **Not in this item.** A home-directory or sqlite store. Resolving
  `next_id` (s191). The allocation floor (s185).

### U9. `next --flag` / `--no-flag` (P3)

- **Problem.** We run a "lite" mode that should skip `risk-*` items, which
  need a model reviewer. `--tree` and `--size` narrow `next`, but flags do
  not.
- **Proposal.** Repeatable `next --flag F` (keep items with any F) and
  `--no-flag F` (drop items with any F), prefix match optional
  (`--no-flag 'risk-*'`). The same on `--batch`.
- **Workaround.** Loop `next -n K` and skip by flag in the script.

### U10. Outline `depends:` cannot name a title that contains a comma (P3)

- **Problem.** Import splits a `depends:` value on commas. A dependency on
  an item titled "Fall back across vendors on a rate limit, halt cleanly,
  resume cold" was reported as three missing titles.
- **Evidence.** Our dry run, 2026-10-04: `problems: ["... depends on 'Fall
  back across vendors on a rate limit', which is not in the outline or the
  index", "... 'halt cleanly' ...", "... 'resume cold' ..."]`. Repeated
  `depends:` lines work.
- **Proposal.** Treat each `depends:` line as exactly one title, and
  document repetition as the way to list several. Alternatively, try the
  whole value as a title before splitting. At minimum, `import.md`'s key
  table should say "comma-separated; repeat the key for a title containing a
  comma", as it does for `tree`.
- **Workaround.** We retitled the item.

### U11. Record that a database is not the source of truth (P2)

Added 2026-10-05. Deduped against slicer's rendered roadmap on `main` that
day: s175, s185, and s191 are open and cover the worktree cases; s184 is
done and already shows sibling review and done work. P2 because we have no
code workaround if the canonical store leaves git: the decision has to land
before any database work.

- **Problem.** Slicer's goals say "git-tracked JSON today; a database
  backing may come later — TBD." Read from this orchestrator, that sentence
  is easy to implement as `~/.slicer/slicer.db`. That store would not travel
  with a run branch, would not clone, would not appear in a PR diff, and
  would be a different directory inside agentbox than on the host. The
  worktree bugs that motivate it are already queued: s175 (commit the
  handoff), s185 (id floor across sibling worktrees), s191 (`next_id`
  merge). A side database would hide the state those items are designed to
  keep in the checkout.
- **Evidence.** Slicer's goals and non-goals, and `ARCHITECTURE.md`: JSON
  under `.slicer/` is canonical, `check` compares bytes, and the render is
  deterministic. This repo's S33 invariants I1 and I2 (commit `.slicer/` on
  every exit; a checkpoint reset must not touch it), N1 (a fresh clone has
  to see the queue), and the 2026-10-04 decision that slicer stays on the
  host for S39. OKF kit, `info/okf-implementation/README.md` points 1 and 4,
  and `bundles/harborline/index.md`: git is the source of truth, and a
  catalog is a projection. `sqlite3` is in the standard library, so this is
  not a dependency objection. It is the branch, clone, review, and
  byte-compare invariants.
- **Proposal.** Replace the TBD with an explicit decision. The canonical
  store stays git-tracked JSON under `.slicer/`. A database, if one is ever
  added, is a rebuildable cache of that JSON, lives inside the checkout, is
  gitignored, and is never read back as authority. `~/.slicer/` is not a
  state directory. Name s175, s185, and s191 as the worktree design. No
  schema, no sqlite module, no new command.
- **Workaround.** None. We keep committing `.slicer/` on the run branch.
- **Not in this item.** Implementing a cache. A merge driver (s191 and U8).
  Typed or trust-filtered notes (U3 and U12).

### U12. Trust-filtered note packs (P2)

Added 2026-10-05. Depends on U3. Does not replace U3's kind filter, and
does not add a database. This is the memory feature for this workflow:
decisions, reports, and lessons stay in the checkout, and a pickup loads
only the ones that are still trusted.

- **Problem.** Decisions, slice-done reports, and review verdicts are one
  note list. A later session either loads all of them or greps prefixes.
  Accepted decisions get missed (SA5). A decision from a finished slice
  keeps spending tokens. Nothing stops a machine-written note from reading
  like an owner decision. U3's kinds separate the labels. They do not say
  who may write a decision, when a note goes stale, or how to pack a few of
  them under a character budget.
- **Evidence.** SA4 and SA5. The OKF kit derives trust instead of storing a
  label: no `verified` is unverified, any other actor is machine-confirmed,
  and a `human:` actor is human-reviewed (`trust_tier` in
  `info/okf-implementation/okf_kit/__init__.py`). `pack_context` drops
  deprecated, draft, under-trusted, and past-`stale_after` concepts, then
  keeps a neighborhood inside a character budget. The Harborline pack for
  "net revenue" keeps the human-reviewed metric and the playbook that says
  to refuse the deprecated gross definition. A generated concept must set
  `generated.by` and must not set `verified`. The kit is an illustration.
  Its packer is a linear scan, which is enough for the note counts we have.
- **Proposal.** On top of U3's `kind`:
  - A note may carry `by` (log entries already have this), a trust tier
    derived the same way (`human:` versus any other actor versus absent),
    and an optional `stale_after`.
  - `show` and `next --ready` accept `--min-trust` and a character budget,
    drop notes past `stale_after`, and return a manifest plus the selected
    texts. The default stays "all current notes", so today's callers do not
    change.
  - An agent-written note cannot set a `human:` actor. Promotion to that
    actor is a separate owner command.
  - U3's `handoff_requires_note_kind: "report"` stays U3's request.
- **Workaround.** U3's kind filter, plus our orchestrator grepping note
  text for a fixed prefix. Stale notes still come along.
- **Not in this item.** Embedding the OKF kit. A PyYAML dependency. A
  catalog database, inside or outside the worktree. Moving the queue out
  of `.slicer/`.

## Contracts selected in the owner interview

- U1 uses a renderer-format revision, not a package-version stamp. Keep
  stale_render as paths and add details; a mismatch does not prove the state
  also stayed unchanged. No optional min_version is included.
- U2 adds an explicit dependency-satisfaction policy with historical done-role
  defaults; status-folder, in-work and Git verification meanings remain intact.
- U3 preserves display-string notes and adds structured note_records. Require
  a nonempty report from the current implementation attempt, not any old report.
- U4 uses validated source IDs. A reused key returns the existing item unchanged,
  even when the retry payload differs. Keys are checkout-local state coordinated
  under the existing writer lock; independent branches do not share a key store.
  Exact-title matching is case-sensitive equality.
- U5 claims a custom queue in place, resumes the effective actor's claimed work
  first, and skips other owners. Explicit start-to permits open, started and
  custom destinations; terminal, parked and review-role destinations are excluded.
  The existing batch/status incompatibility remains.
- U6 counts fresh implementation starts once; rejection and resume do not count.
  Historical counts are preserved for owner correction. Caps limit new attempts,
  allow active attempts to resume, and do not change statuses automatically.
- U7 provides timezone-aware inclusive since and exclusive until filters only;
  no cursor or exact-clock-skew run boundary is promised.
- U8 extends s191's driver conservatively. Different items/fields can combine;
  incompatible lists, deletions versus edits and queue reorders remain conflicts.
  The driver must reject allocation/key collisions and retain real integrity checks.
- U9 includes case-sensitive shell-style patterns, OR inclusion, exclusion
  precedence and batch support. Quote wildcard patterns when calling from a shell.
- U10 tries the whole dependency title first, falling back to comma splitting.
  Repeated lines remain supported and preview/application share one resolution.
- U11 adopts git-tracked .slicer JSON as permanent authority. Any future database
  is an ignored, rebuildable checkout-local projection, never read as authority.
  This filing specifies the future documentation change; it does not create a cache.
- U12 preserves author by and derives trust from separate verified_by evidence.
  Human verification uses a separate owner attestation command, acknowledged as
  a workflow convention rather than authentication. Text edits clear verification.
  Packs cover only the selected item, favor higher trust then newest, and skip
  whole over-budget notes. Either min-trust or notes-budget opts into packing and
  expiry filtering; ordinary reads retain complete audit notes. Batch budgets
  apply independently per item. A kind filter alone does not activate expiry.
